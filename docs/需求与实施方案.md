## 一、架构速览

开始改动前必须理解的四个不变量：

1. **分层**：`src/model`（解析/改写 Markdown）与 `src/layout`（布局计算）**不依赖 DOM，也不依赖 Obsidian API**。这是它们能被 Node 直接测试的原因。新增逻辑应尽量下沉到这两层。
2. **往返改写**：导图对笔记的修改采用"行区间替换"，保证只动目标行、其余字节不变。任何写回功能都必须遵守。
3. **单一视图**：插件不创建新文件，只在同一个 leaf 上切换 view type，直接读写原 `.md`。
4. **测试与源码同目录**：`npm test` = `node --test "src/**/*.test.ts"`，共 23 个测试文件、311 条用例。

## 二、需求细化

### 需求 1 — 快捷键与节点类型

#### 1.1 添加快捷键（基础设施）

**现状**：快捷键注册表在 `src/view/shortcuts.ts:202-345`，共 23 个 action。用户自定义绑定存在 `settings.shortcuts`，只存改过的项，合并逻辑在 `shortcuts.ts:396-412`（`resolveBindings`）。作用域分两处：视图作用域只绑 search/close-search（`MindmapView.ts:410-461`），其余全部走 viewport 的 keydown 分发（`interactions.ts:352-484` → `resolveAction`）。

**结论**：新增快捷键**不需要**动分发机制，只要在 `TABLE` 里加一行，再在消费端接一个 handler 即可。测试 `src/view/shortcuts.test.ts` 会自动校验"每个 action 都有条目且可查到""没有两个 action 抢同一个键"，加错了会直接红。

#### 1.2 注解快捷键 `Ctrl+Enter`

**现状**：注解体系已经完整，唯独**没有快捷键**。

- 判定与解析：`src/model/annotations.ts:4`（正则 `ANNOTATION`）、`:7-17`（`isAnnotationLine`，允许列表项内容列 +4 空格内）、`src/model/parse.ts:215-237`（挂载到模型）
- 渲染：`src/view/nodes.ts:280-290`，输出 `.mm-text.mm-annotation`
- 已有专用对话框：`src/view/annotationDialog.ts:5-52`（textarea，`Ctrl/Cmd+Enter` 保存）
- 现有入口：双击注解（`interactions.ts:158-161`）、右键菜单（`MindmapView.ts:2023-2028`）、`editAnnotation`（`MindmapView.ts:2454-2473`）

**目标**：`Ctrl+Enter` 在选中节点下新建一条注解行并直接进入编辑态；已有注解时进入编辑而非新建。

**改动点**：`shortcuts.ts` TABLE 里 `edit-annotation` 行（默认 `Ctrl+Enter`）；消费端在 `MindmapView.bindScope()` 里接 `editAnnotation(id)`，复用 `src/model/mutate.ts` 的行插入能力。

**注意**：`Ctrl+Enter` 在 Obsidian 编辑器里是「切换复选框状态」，而且会被 keymap 管线先一步吃掉、到不了 viewport 的 DOM keydown 监听器 —— 所以这个 action 必须走视图 scope 注册（`MindmapView.bindScope()`），不能只依赖 `resolveAction` 分发。需在 `shortcuts.test.ts` 确认不与其他 23 个 action 撞键。

#### 1.3 大块文字/代码块子节点 `Shift+Enter`

**现状（这是本需求最大的坑）**：插件已有"正文卡片"体系，但它是**只读的虚拟节点**。

- 开关：`showBodyNodes`（`settings.ts:237-240`）
- 构建：`childrenOf`（`MindmapView.ts:993-1009`）+ `makeBodyNode`（`:1011-1043`），把 `bodyRanges` 合成 `kind:"body"` 的虚拟节点
- **致命点**：这些节点**不在 `parsed.byId` 里**（`MindmapView.ts:988-992`），因此改名/移动/删除/缩进**全部静默失效**，只能回到编辑器改
- `src/view/blockDialog.ts` 是正文块的整块读/编辑对话框，用 Obsidian 官方 `MarkdownRenderer.render`（`:185`）——**这是全插件唯一能正确渲染表格、围栏代码块、`\begin{align}` 的地方**；普通节点只走自研行内渲染
- 代码块类卡片走 `preformatted`（`MindmapView.ts:1147` → `nodes.ts:223-225`，纯文本 + `data-block="pre"`）

**目标**：`Shift+Enter` 在选中节点下插入一个"缩进块"子节点——只靠缩进表达从属关系，不带任何 Markdown 标记符号（不是引用、不是列表符号），内部可放长文本或代码，且**在导图里可编辑**。

**改动点（需要新写写回路径）**：
1. `src/model/mutate.ts` 新增 `insertIndentedBlock(parentKey, text)`——按父节点行的缩进 + `indentUnit` 计算子块缩进，插入纯文本行
2. 让 `makeBodyNode` 产出的虚拟节点支持编辑：要么给虚拟节点补一个 `byId` 条目，要么新增 `kind:"block"` 类型走独立的编辑/删除路径
3. 编辑 UI 复用 `blockDialog.ts`（它已有 read/edit 双页签和官方渲染管线）

**风险**：高。触及"虚拟节点不可变"这一核心假设，且必须保证往返改写不破坏原笔记格式。

#### 1.4 导图节点 ↔ md 标签/代码块双向定位 `Ctrl+点击`

**现状**：**全仓没有任何节点↔md 行号的定位能力**（无 `revealLine`、无 `setCursor`）。现有的 `Ctrl/Cmd+点击` 语义由 `Keymap.isModEvent` 决定，行为是**在新标签/新分栏打开该链接**（`MindmapView.ts:1975`、`blockDialog.ts:173`）。

**目标**：`Ctrl+点击` 一个节点，跳到 md 文档中对应的行/代码块；反向也要能从 md 行定位到导图节点。

**改动点**：
1. 模型层已有行号信息（`src/model/parse.ts` 产出节点时记录了行区间），先确认 `src/model/types.ts` 是否暴露了 `line` / `lineEnd`
2. 正向：`Ctrl+点击` → 取节点行号 → `leaf.setViewState("markdown")` + `editor.setCursor` + `editor.scrollIntoView`
3. 反向：需要新增一个 md 侧入口（命令或编辑器右键），由光标行反查节点 key
4. 与现有 `Ctrl+点击`（打开链接）冲突，需要区分：链接节点走原逻辑，普通节点走跳转逻辑

### 需求 2 — 保存工作区状态

**现状**：

- `foldStore` 存的是 `NoteViewState`，字段只有 `collapsed`（折叠的节点 key 集合）、`focusKey`、`focusId`、`at`（时间戳）—— 见 `src/foldStore.ts:16-35`
- **不含缩放/平移**：canvas 相机状态完全不持久化
- 存储位置：`data.json` 顶层保留键 `"foldState"`（`main.ts:27`、`:280`），内层 key 是笔记的 vault 路径，上限 200 条（`prune`，`foldStore.ts:96-106`），超限按 `at` 淘汰
- 读写链路：`rememberState`（`MindmapView.ts:897-911`）、`seedFolds`（`:836-865`）、`writeNoteState`/`readNoteState`（`main.ts:291-307`）；笔记重命名/删除会跟随（`main.ts:185-199`）
- **没有"记住某笔记上次是导图视图"的能力**：视图类型由 Obsidian 自己的 leaf viewState 恢复；插件侧只有 `previousState` 这个 `WeakMap`（`main.ts:57`），仅用于同一 leaf 切回 md 时还原阅读/源码模式（`main.ts:359-373`）

**目标**：从其他文档切回一个"进过导图"的文档时，直接展示导图；并可选地跨 Obsidian 重启持久化。

**需要实测确认的前提**：如果 leaf 一直开着，Obsidian 从 `workspace.json` 恢复 leaf state 时**本来就会恢复成导图**。所以本需求真正要解决的是"笔记被关掉后重新打开"的场景。开工前先实测一次，避免做重复功能。

**改动点**：
1. `foldStore.ts` 的 `NoteViewState` 增加 `view: "mindmap" | "markdown"` 字段（或新增独立集合 `mindmapNotes: string[]`）
2. `main.ts` 的 `setMindmapView` / `setMarkdownView` 里记录
3. 监听 `workspace.on("file-open")`：若该笔记在集合中且设置开关打开，自动切导图
4. `settings.ts` 增加开关，区分"会话缓存"（内存，重启用失效）和"永久缓存"（写 data.json）两档
5. 相机状态（缩放/平移）若要一起持久化，`NoteViewState` 需扩展 `scale` / `tx` / `ty`

**风险**：中。自动切换视图可能让用户困惑（"我只是想看 md"），建议默认关闭 + 提供"临时切换后不再自动跳"的抑制逻辑。

### 需求 3 — 界面/工具栏

#### 3.1 工具栏位置可调/可拖动

**现状**：`buildToolbar`（`MindmapView.ts:678-713`）。DOM 结构是 `contentEl` 下的 `.mm-toolbars`，内含两个 `.mm-toolbar`（`-export` 和 `-camera`）。定位在 `styles.css:743-753`：`position:absolute; right:12px; bottom:12px; z-index:10`。

**目标**：支持放在底部/右侧，并可自由拖动。

**改动点**：
1. 把绝对定位改成 CSS 变量驱动（`--mm-toolbar-x` / `--mm-toolbar-y`），坐标存进设置
2. 加拖动交互（pointerdown/move/up），复用 `src/view/motion.ts` 的 `will-change` 机制
3. 设置项加"停靠位置"枚举：右下 / 底部居中 / 右侧垂直

**注意**：工具栏挂在 `contentEl` 上、在 `.mm-viewport` **外面**，这是为了不被导出截图带上。拖动实现不能破坏这一点。

#### 3.2 导出功能合并为单个按钮 + 二级菜单

**现状**：导出有 4 个独立按钮（`MindmapView.ts:701-703`），统一清单在 `src/export/run.ts:31-60`（`EXPORT_COMMANDS`）。

**改动点**：把 4 个按钮换成一个，点击弹出二级菜单（复用 Obsidian 的 `Menu`，或自绘浮层）。清单仍从 `EXPORT_COMMANDS` 读，保证命令面板入口不受影响。

#### 3.3 去掉右上角菜单里的重复导出

**现状**：导出共 **3 个入口** —— 工具栏（`MindmapView.ts:701`）、标签页右键菜单 `onPaneMenu`（`:634-642`）、命令面板（`main.ts:141-152`）。

**改动点**：移除 `onPaneMenu` 里的导出项（`:634-642`）。命令面板入口保留——它不是冗余，而是让用户可以绑快捷键，且符合 Obsidian 惯例。

### 需求 4 — 功能优化

#### 4.1 自定义设置窗口

**现状**：`settings.ts` 用 Obsidian 标准 `PluginSettingTab`，`GROUPS`（`:165-291`）三组 13 项。为了兼容 Obsidian 1.13 新 API 和老版本，维护了**双渲染路径**（新版 `getSettingDefinitions` `:324` / 旧版 `display` `:358`）。

**目标**：改成自定义模态窗口，因为设置项多、需要分类，且想做"菜单栏定向"。

**改动点**：新建 `src/view/settingsModal.ts`，用 `Modal` 类。设置项定义从 `GROUPS` 抽成纯数据（可被两种 UI 共用），避免逻辑重复。

**建议**：保留标准 `PluginSettingTab` 作为兜底（Obsidian 的"设置 → 第三方插件 → 选项"入口会调用它），自定义窗口只做增强入口。否则从 Obsidian 设置面板点进来会没有反应，用户会以为插件坏了。

#### 4.2 多种导图样式（单/双侧切换、直角分支）

**现状**：

- 布局**已支持**两种：`balanced`（双侧）/ `right`（单侧），在 `src/layout/tidyTree.ts:211-247`，双侧切分逻辑 `:190-209`。所以"单/双侧切换"**已经存在**，只需确认 UI 入口是否好找
- **无直角/曲线开关**：连线固定为三次贝塞尔 S 曲线（`src/view/edges.ts:70-76`），线宽按深度递减（`:26-30`），锚点计算 `anchorFor`（`:18-24`）

**改动点**：`edges.ts` 增加连线样式分支——在 `anchorFor` 和路径生成处按样式产出 `M...L...L` 的直角折线（典型做法：父锚点 → 水平中段 → 子锚点）。设置项加 `edgeStyle: "curve" | "orthogonal"`。

**注意**：`edges.ts` 有配套测试 `src/view/edges.test.ts`，新增样式要同步补用例。直角分支在双侧布局下需要根据子树方向镜像折线，这是最容易出视觉 bug 的地方。

#### 4.3 双击选中节点才弹出编辑栏

**现状**：**没有"选中后出现的编辑栏"**。节点自带工具行 `.mm-tools`（含 toggle 和加号）是**常驻 DOM** 的（`nodes.ts:250-274`），显隐靠 CSS hover 控制。选中态只是加一个 `.is-selected` 类（`MindmapView.ts:1684-1689`）。

**改动点**：把 `.mm-tools` 的显隐从 CSS `:hover` 改为受选中状态驱动；设置项加"编辑栏常驻/按需"开关。改动集中在 `nodes.ts` + `styles.css`，风险低。

#### 4.4 拖动节点时实时预览（半透明跟随）

**现状**：**没有拖动预览/幽灵元素**。拖动时只给源卡片加 `.is-dragging`（`interactions.ts:296-305`），给目标位置加 `is-drop-target` / `before` / `after` 类（`:236-260`），真正的节点移动在 `pointerup` 时一次性完成（`finishDrag` `:315-334` → `move` `MindmapView.ts:1944-1963`）。`src/view/motion.ts` 只负责 `will-change` 优化，与拖动预览无关。

**改动点**：
1. `interactions.ts` 的 pointermove 中新增一个"拖拽幽灵"元素（半透明克隆卡片 + 跟随光标 + 落点指示线）
2. 复用 `motion.ts` 的 `will-change` 机制避免掉帧
3. 注意与裁剪（culling）和虚拟滚动共存——节点可能被回收

**风险**：中。大图下每次 pointermove 都重绘会掉帧，建议用 `transform: translate()` 走合成层，不要改 `left/top`。

#### 4.5 选中后按 Backspace 删除整个节点（含子节点）

**现状**：**功能已经存在**。`removeNode`（`MindmapView.ts:1866-1874`，根节点会被拒绝），快捷键 `delete-node` 默认绑定 `Delete` 和 `Backspace`（`shortcuts.ts:222-226` → `interactions.ts:448-452`），右键菜单也有入口（`MindmapView.ts:2077-2084`）。

**结论**：这条**可能不需要开发**。需要你确认的是：当前 Backspace 是否**只删当前节点、把子节点提级**，而你希望**连同子节点一起删**？如果是要改成级联删除，那才是真正的改动点，且建议加二次确认或保留撤销。

#### 4.6 撤销在任何情况下都能执行（修 bug）

**现状**：`apply` 压栈（`MindmapView.ts:1702-1711`，`UNDO_LIMIT` 截断），`undo`/`redo`（`:2150-2165`），`saveBody` 单独压栈（`:2550-2553`）。

**四个失效场景**（按可疑度排序）：

| # | 场景 | 位置 |
|---|---|---|
| ④ | **最可疑**：`editingId` 在 `beginEdit` 置位（`:1770`）、在 `finish` 清除（`:1805`）。若编辑中的卡片被重绘/裁剪（`paint` 会重建全部元素，`:1091-1154`），`finish` 的 blur/keydown 永不触发 → `isEditing()` 恒为 `true` → keydown 处理器直接 return，撤销彻底失灵 | `interactions.ts:353` |
| ③ | keydown 挂在 `canvas.viewport` 上（`interactions.ts:352`），只有 viewport 持 DOM 焦点才触发。点击卡片会 `viewport.focus()`（`:149`），但点 `.mm-tools` / `.mm-checkbox` / `.mm-expand` / `.mm-add` 时 `stopPropagation` 且**不聚焦**（`:119-146`），焦点留在 `body` → 含 `Mod+z` 的所有快捷键静默失效 | `interactions.ts:119-146` |
| ① | 切换文件时清空撤销栈 | `MindmapView.ts:501-502` |
| ② | 文本相同不压栈 | `:1706` |

**改动点**：先复现定位（大概率是 ④），修法是让 `paint` 重建元素时保留/恢复编辑态，或在 `paint` 前强制 `finish` 当前编辑。③ 的修法是让那些按钮点击后也聚焦 viewport，或把 keydown 提到更外层容器。

### 需求 5 — 中英文国际化（i18n）

**现状**：**完全没有 i18n 机制**（全仓 grep `i18n|locale|getLanguage` 零命中；`translate` 是布局函数，与语言无关）。用户可见字符串硬编码散落，合计 **200 处以上**：

| 位置 | 量级 |
|---|---|
| `src/view/shortcuts.ts:202-345` | 23 个 action × (name + description) ≈ 46 处 |
| `src/settings.ts:165-291` + `:129-151` + `:294` | ≈ 40 处 |
| `src/view/MindmapView.ts`（菜单 `:2017-2085`、工具栏 label `:705-712`、pane 菜单 `:618-642`、快捷键面板 `:723-756`、Notice `:1766/1869/2153/2466`） | ≈ 45 处 |
| `src/main.ts:80-163` 命令名 + `:226`/`:344` | 10 处 |
| `src/export/run.ts:90-146` | 7 处 |
| `blockDialog.ts:77-96`、`annotationDialog.ts:27-50`、`searchBar.ts:52`、`updateNotice.ts` | ≈ 25 处 |

**目标**：支持中英文，跟随 Obsidian 语言设置。

**建议方案**：
1. 新建 `src/i18n.ts`：`t(key, params?)` 函数 + `zh` / `en` 两份字典
2. 语言检测用 `window.localStorage.getItem("language")`（Obsidian 存语言的地方），回退到 `moment.locale()`，再回退到 `en`

#### 4.6 的真实成因（与初次调研的推断不同）

初版方案里我怀疑是 `editingId` 卡住。**实际成因在编辑器的按键监听里**（`MindmapView.ts` 的 `beginEdit` 内）：

```ts
el.addEventListener("keydown", (ev) => {
    ev.stopPropagation();   // 每个键都在这里被拦下
    ...
});
```

它无条件 `stopPropagation`，于是**按键根本到不了视口的处理器** —— 而视口处理器才是「一次按键变成一次动作」的唯一入口。所以撤销从来没被执行过；而平台自己的 contenteditable 撤销，在一个刚被清空的字段上，什么也撤不了。

用户描述的「选中节点后撤销失效」实际是：`Tab` 或 `Enter` 新建节点后，新节点**同时处于选中态和编辑态**（`beginEdit` 里既 `setEditingId` 又 `select`），所以看起来像「选中导致的」。

#### 修法

把撤销/重做**按名字送到导图**，而不是让它冒泡 —— 这与该文件里 Ctrl/Cmd+F 的既有做法一致（`stopPropagation` 把一切拦在边界上，所以被放行的键只能被「carry」过去）。且只在**尚未输入任何字符**时放行：

- 新增纯函数 `survivesEditing(action, typed)`（`src/view/shortcuts.ts`），配独立测试。一旦输入过字符，卡片就有自己的东西要撤销，平台的撤销才是正确答案；在此之前，用户想撤销的是「新建」这个动作本身。
- `MindmapView` 记录编辑中的标题元素与它打开时的原文，作为「是否输入过」的判据。**从元素读取而不是用 input 监听器追踪**：漏掉任何一条路径（粘贴、拼写纠正、字段内撤销）都会让判断与屏幕不符。
- `undo` / `redo` 在移动栈之前**先关闭空闲的编辑器**。这不是可选项：重绘会带走编辑器所在的元素，而一个永不触发的 blur 会让 `editingId` 卡住，此后导图对所有按键失聪。

#### 顺带修的同类缺陷

折叠按钮和复选框都是普通 `div`，点击后焦点掉到 `body`，键盘同样失灵（点卡片不会，因为兜底分支会把焦点拿回来）。两处现在都把焦点放回视口。**新建按钮和展开按钮刻意不在此列** —— 它们要把焦点交给自己打开的东西（编辑器 / 对话框）。

验证：`npm run check` 全绿，**326 条测试通过**（新增 2 条）。新增的测试遍历整张快捷键表而不是写死 undo/redo，所以以后新增的 action 不会悄悄混进这个例外。

#### 追加：切换 MD / 导图后撤销历史丢失

用户在实测撤销修复时发现的第二个问题，**不是需求里的条目，是真 bug**。

**成因**：插件的视图切换走的是 `leaf.setViewState()`（这是它的核心设计 —— 不创建新文件、在同一个 leaf 上换视图类型）。Obsidian 会因此**销毁旧的 `MindmapView` 实例**，撤销栈随实例一起消失；切回来时是**全新实例**，`setViewData(data, clear=true)` 里把两个栈清空。所以历史丢失不是逻辑写错，是「栈只活在视图里」这个结构的结果。

**修法（最终版）：一篇笔记一份历史，两个视图共用。**

最初我做的是「文档变了就丢弃历史」—— 安全，但结果是**在 MD 里做的编辑根本无法从导图撤销**。用户明确指出这不对：他要的是**统一的修改栈**，谁写的都进同一个栈，按落笔顺序回退。

- 新增纯模块 `src/undoPark.ts`（+ 14 条测试），承载全部规则。`UNDO_LIMIT` 也移到这里，视图和监听器花同一份预算。
- `MindmapView.commit()` 里**每次写入都寄存**，而不是在 `onClose` 里寄存。原因：视图的销毁顺序不可依赖，`clear()` 会在视图还没结束时就把 `data` 清成 `""`，走「离场时寄存」这条路可能什么都存不到。
- `setViewData` 的 `clear` 分支取回历史。

**三个规则（`undoPark.ts` 里都有测试）**：

1. **`takeUndo` 不再因文档变化而丢弃历史。** 历史手里那个版本本身就是一次合法的回退，所以它**入栈成为一步**，历史继续往下走。这就是「统一栈」的核心：MD 里的编辑会由导图的撤销按顺序回退。
2. **`recordExternalEdit` 记录「历史不知情的变化」** —— MD 编辑器、第二个窗口、同步客户端。**内容与已记录的相同则不算变化**，这一步很关键：导图自己的保存会原样回传，若把它当成一步，每次按键和上一次之间都会插进一个撤销点。
3. **插件监听 `vault.on("modify")`**，把该笔记的每次外部变化折进栈里，所以一次 MD 编辑会话会变成**一串步骤**而不是一次大跳。读文件是一次事件循环往返，所以前一次没回来就不再发起第二次 —— 两次乱序返回会把版本记反。

**关于安全性的取舍（与原设计相反）**：原设计怕的是「撤销抹掉用户在 MD 里的编辑」。但**这正是撤销该做的事** —— 而且 redo 可以还原。所以现在的规则是「入栈」而不是「丢弃」。

| 场景 | 行为 |
|---|---|
| 导图 → MD（只读）→ 导图 | ✅ 历史原样保留 |
| 导图 → MD（编辑了）→ 导图 | ✅ 历史保留，**多一步**；`Ctrl+Z` 回退那次 MD 编辑，再按回退导图的编辑 |
| 导图与 MD 同时打开同一笔记 | ✅ 两边写进同一个栈（视图侧在 `setViewData(clear=false)` 时也记录外部变化） |
| 导图 A → 笔记 B → 导图 A | ✅ A 的历史还在（路径不匹配时**不清空**槽位） |
| 同一笔记开两个导图视图 | 各自独立（取回后槽位即**消费掉**，共用数组会互相撤销） |

槽位只有**一个**，不是按路径建表：值得付出代价的场景就是「来回切换」，而每篇笔记 100 个快照（`UNDO_LIMIT = 100`）不值得为整个 vault 常驻。栈里存的是字符串引用，所以寄存的实际开销只是一个指针数组。

**刻意没做的一件事**：**MD 编辑器里的 `Ctrl/Cmd+Z` 仍然是 CodeMirror 自己的。** 要接管它，需要 `@codemirror/commands` 的 `undoDepth` 来判断「编辑器自己已经没东西可撤销了」—— 只有这样接管才不会破坏用户正常的逐词撤销。但那个 import **不属于 Obsidian 公开 API**，一旦运行时解析不到，插件会直接加载失败。我在这里无法启动 Obsidian 验证，所以没做。**结果是：历史是连续的，导图的撤销能回退 MD 的编辑；但「人在 MD 里按 Ctrl+Z 去撤销一次导图编辑」这条路径不通。** 详见「需要你知道」。
