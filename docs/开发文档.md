# MindFlow 开发文档

> 英文版：[Development.md](Development.md) ｜ 使用说明：[使用指南.md](使用指南.md)

这份文档写给要读代码、改代码的人。它讲清楚三件事：**代码怎么分层**、
**为什么这么分层**、**要加东西时该动哪里**。

---

## 1. 一句话概括

MindFlow 是笔记的一种**视图**，不是导出器。它把 markdown 解析成一棵树显示在画布上，
你在画布上做的每一次修改，都会被翻译成对原文的**行范围拼接**，写回同一个文件。

核心不变量只有一条：

> **文件永远不从树重新生成。** 每个节点都记着自己来自哪一行、那一行由哪些片段
> 组成，所以它能逐字符重建自己。没被编辑过的行，逐字节原样返回。

这条不变量是整个项目的地基，测试套件专门守着它。

---

## 2. 模块分层

```
src/model/     解析器 + 变更引擎 —— 纯函数，不 import Obsidian，也不碰 DOM
src/layout/    tidy-tree 布局 —— 同样零依赖
src/view/      画布、卡片、连线、交互、公式、TextFileView
src/main.ts    插件入口：视图注册、模式切换、命令
src/settings.ts / src/i18n.ts / src/foldStore.ts / src/undoPark.ts   横切关注点
src/export/    四种导出格式
```

### 为什么这么分

`src/model` 和 `src/layout` **既不依赖 DOM 也不依赖 Obsidian**。这不是洁癖，而是
可测试性的前提：它们可以直接用 `node --test` 跑单元测试（Node 22.6+ 原生剥离
TypeScript 类型 —— 不需要构建步骤，也不需要测试框架）。

`src/view` 是唯一允许碰 Obsidian API 和 DOM 的地方。它很厚（`MindmapView.ts`
是最大的文件），因为渲染、布局、选择、撤销、搜索、弹层、导出都挂在同一个
`TextFileView` 生命周期上。

## 3. 模块清单

### `src/model/` —— 纯函数层

| 文件 | 职责 |
| --- | --- |
| `lines.ts` | 行数组与文本之间的互转，以及 `spliceLines` 这个核心拼接原语 |
| `parse.ts` | markdown → 节点树。状态机处理围栏代码、ATX 标题、列表、正文块 |
| `types.ts` | `MindNode` / `ParsedDoc` / `NodeKind`，以及缩进宽度换算 |
| `mutate.ts` | 所有变更：增删改、移动、重排、缩进、复选框、注解、文字块 |
| `releveling.ts` | 把一棵子树重写成新父级所需的标记形态（跨标题/列表边界时用） |
| `annotations.ts` | `: text` 行的识别与拆分 |
| `inlineText.ts` | 行内 markdown 的分词（粗体、代码、链接、公式……） |
| `media.ts` | 判断一个嵌入指向的是图片还是视频，以及 `![[…]]` 里的路径、别名和 `\|300` 尺寸 |
| `blocks.ts` | 把一段正文范围拆成它由哪些块组成 —— 段落、代码、表格、callout —— 以及其中哪些是卡片没法当纯文本画的 |
| `replace.ts` | 在树上做查找替换：先出一个计划，再把整个计划当成**一次**编辑写回去 |
| `noteName.ts` | 把节点文本变成一个合法的笔记名，以及把 `[[链接]]` 读回它的目标和标签 |
| `search.ts` | 在树上做子串 / 正则匹配，以及折叠相关的辅助计算 |

**`spliceLines` 是所有写入的唯一出口。** 想改文件，就得先算出「从第几行删几行、
插入什么」，再交给它。没有第二条路径。

**解析器对格式很宽容，但只在读的方向。** 比如列表项紧跟的缩进段落，CommonMark
会当成懒续行，这个解析器能正确区分；但写回时仍然按规范写（见
[§7 已知取舍](#7-已知取舍)）。

### `src/layout/`

`tidyTree.ts` —— 经典的 tidy-tree 布局。输入节点树，输出每个节点的位置、宽高、
所属分支号。均衡模式下按重量把顶级分支分到根节点两侧。

### `src/view/`

| 文件 | 职责 |
| --- | --- |

| `nodes.ts` | 把 `MindNode` 变成 DOM 卡片 |

## 4. 一次编辑的完整路径

以「在导图上按 `Tab` 加一个子节点」为例：

```
interactions.ts   keydown → resolveAction → "add-child"
       ↓
MindmapView.addChildTo(id)
       ↓
withNode(id, cb)                       // 取出 parsed 和 node
       ↓
model/mutate.ts  addChild(parsed, node, "")
       ↓                               返回 { text, focusLine, ok }
MindmapView.apply(mutation)
       ↓
pushRevision(undoStack, this.data)      // 撤销栈入栈
       ↓
commit(text, focusLine, edit=false)
       ↓
   ├─ data = text
   ├─ parkHistory()                     // 把栈寄存在插件上（跨视图存活）
   ├─ requestSave()                     // 防抖写盘
   └─ render("edit")                    // 重新解析 + 重绘
```

关键点：

- **`apply` 是唯一的写入闸门。** 它负责入栈、清空 redo、提交、重绘。任何变更函数
  都只返回一个 `Mutation`，不自己动文件。
- **`Mutation.ok === false` 表示拒绝**，此时 `text` 是原文，`apply` 直接返回，
  不产生撤销步骤。拒绝的原因（比如节点不在笔记里）由调用方决定怎么告诉用户。
- **`focusLine` 是变更后应该选中的行号**，`-1` 表示不动选择。

## 5. 加一个快捷键

快捷键体系的设计目标是：**一张表，三个读者，不可能漂移。**

`src/view/shortcuts.ts` 里的 `TABLE` 是唯一真源：

```ts
const TABLE = [
    { action: "add-child", defaults: ["Tab"] },
    { action: "add-sibling", defaults: ["Enter"] },
    // …
] as const;
```

三个读者：

1. **`interactions.ts` 的 keydown 处理器** —— 用 `resolveAction()` 把一次按键解析
   成 action，再 `switch` 分发；
2. **设置页 / 设置窗口** —— 每个 action 渲染一行，可以录制、清除、恢复默认；
3. **导图里的快捷键面板**（工具栏的 **?**）—— 打印当前实际绑定的按键。

### 加一个动作要动四处

1. `TABLE` 加一行 `{ action, defaults }`；
2. `i18n.ts` 加两条：`shortcut.<action>.name` 和 `shortcut.<action>.description`；
3. `interactions.ts` 的 `switch` 加一个 `case`（`default` 分支里的
   `assertHandled(action: never)` 会**编译报错**提醒你漏了）；
4. `MapController` 接口加对应方法，`MindmapView` 实现它。

**第 2 步漏了会编译不过** —— 因为 `shortcutNameKey()` 的返回类型是从 action 名
派生的模板字面量类型（`` `shortcut.${action}.name` ``），只有字典里真有这个 key
才成立。这是刻意的：让「加了动作但没写文案」变成编译错误，而不是界面上一个空白
标签。

### 一个容易踩的坑：带修饰键的组合会被 Obsidian 的 keymap 抢先

视口上的 `addEventListener("keydown", …)` **收不到某些带 `Mod` 的组合键** ——
Obsidian 的 keymap 管道在事件到达 DOM 监听器之前就把它处理掉了。`Ctrl+Enter`
就是这样。

判断方法：在这个处理器最前面打一行日志，如果按了组合键完全没有输出，就是被
抢先了。

解法：把那个动作注册到 Obsidian 的 **`Scope`** 上，而不是只挂在 DOM 监听器上：

```ts
for (const combo of bindings["edit-annotation"]) {
    this.registerScoped(scope, combo, (evt) => {
        const id = this.selectedId();
        if (!id || this.isEditing()) return true;   // true = 放行
        evt.preventDefault();
        this.editAnnotation(id);
        return false;                               // false = 已处理，不再传播
    });
}
```

`search`（`Ctrl+F`）和 `close-search`（`Esc`）从一开始就是这么注册的 —— 这是一个
信号：**带修饰键的绑定走 scope，纯字符键走 DOM 监听器。**

## 6. 加一个设置项

1. `settings.ts` 的 `MindmapSettings` 接口加字段；
2. `DEFAULT_SETTINGS` 加默认值；
3. `GROUPS` 数组里加一行（`name` / `desc` / `control`）；
4. `i18n.ts` 加对应的 `settings.<key>.name`、`settings.<key>.desc`，
   下拉框还要加 `settings.<key>.option.<value>`。

改完之后：设置窗口和 Obsidian 原生设置页会同时出现这一项（两个渲染器读同一个
`GROUPS`），并且**自动触发重绘** —— `SettingsPanel.commit()` 里除了语言和标题栏
按钮两个特例，其余 key 都会调 `plugin.refreshAllViews()`。

如果这一项需要额外的副作用（比如刷新标题栏按钮），在 `applySideEffects()` 里加
分支。

## 7. 已知取舍

这些是刻意的选择，不是疏漏。改之前先读一遍理由。

| 取舍 | 理由 |
| --- | --- |
| **文字块不带空行** | 早期版本在块前加一个空行，为的是 CommonMark 兼容（紧邻列表项的段落是懒续行，别的工具可能把块吞进标题）。用户要求去掉空行 —— 本项目的解析器足够宽容，Obsidian 阅读视图也能正确处理。 |
| **`$…$` 比 Obsidian 严格** | 内容不能以空白开头/结尾，结尾 `$` 后不能紧跟数字。这样才能让 `$5-$10` 保持是价格，代价是 `$x$2` 不渲染。规则住在独立的零依赖模块里，方便单独测。 |
| **正文卡片不能改名/拖动/删除** | 它们代表笔记自己的行，导图只是显示。选中后按 `Delete` 是例外 —— 那确实会删掉对应行。 |
| **`Space` 一个键两个意思** | 按住 + 鼠标左键 = 平移画布（图形工具的老习惯），单击**松开** = 折叠。折叠改成松开触发只是为了把「按住」这一半让出来；这次按住里一旦按过鼠标左键，折叠就丢掉 —— 那一下是平移，不是折叠。键名不跟绑定走：平移键是修饰键，和 `Shift` 同类，不提供「改绑修饰键」。 |
| **均衡模式下重排到分界点另一头会换边** | 笔记里的顺序就是阅读顺序（先右列、后左列），布局按子树重量把这个顺序切成两半分到两侧 —— 顺序由用户定，边跟着顺序走。早期版本不允许顶级分支参与重排，代价是拖到顶级卡片上永远判成「改父级」，比换边糟得多。 |
| **折叠状态按标题路径找回** | 所以给节点改名会丢掉它原来的折叠位置。换成按行号或按 id 都会在编辑后失配得更厉害。 |
| **MD 编辑器里的 `Ctrl+Z` 不接管** | 需要 `@codemirror/commands` 的 `undoDepth` 判断「编辑器自己是否还有东西可撤销」，而那不属于 Obsidian 公开 API。解析不到会让插件直接加载失败，无法在此环境验证 —— 不做。 |
| **撤销栈挂在插件上** | 视图切换走 `leaf.setViewState()`，Obsidian 会销毁旧视图实例。栈只活在视图里就会随实例消失。`undoPark.ts` 把栈寄存在插件上解决这件事。 |
| **只画笔记库里的图片** | `![](https://…)` 保持标签。画远程图片等于让导图替你联网，而且导出时内嵌不进去（跨域读不到字节）。 |
| **导出不内嵌视频** | 一分钟 1080p 转成 base64 就是上百 MB，那不是导出。导出时视频退回成文字标签。 |
| **图片尺寸显式写成像素** | 卡片是 `max-content`，图片若交给 `max-width` 自己算，它的固有宽度会被算进卡片宽度再被钳一次，两者差的正好是那个钳值。 |
| **媒体尺寸跨重绘缓存** | 每次绘制都会重建全部卡片。不缓存的话，每敲一个键图片都会先空着、再触发一次重排。缓存与 MathJax 的缓存同一时刻清空。 |
| **剔除中的卡片不加载图片** | 被剔除的卡片是 `display: none` 而不是不在 DOM 里，`src` 若立即生效，每敲一个键都会重新拉取整篇笔记的图片。加载由 `activateMedia()` 在卡片真正上屏时启动。 |
| **点图片是预览，不是打开文件** | 打开文件要离开导图去另一个标签页，而「看一眼这张图」不该付这个代价。文件本身仍在 `Ctrl`/`Cmd`+点击（以及视频的 `⧉`）后面，只是不再是默认动作。 |
| **预览最多放大到 2 倍** | 卡片把图钳在 200 像素高，所以照片和截图在预览里必然是实打实的放大。这个上限只在图本身很小时才起作用 —— 再往上就只是把像素拉糊，填满面板反而更难看清。 |
| **落点要么整组收下、要么不收** | 一半的拖动比不动更糟。会让一组里某几张落不下的落点，干脆不作为落点提供，于是拖拽兜底到能收下全部的那个，而不是悄悄搬走它搬得动的部分 —— 组里有任何一个走不了，整组都不动。 |
| **空白处直接拖动默认是框选** | 画布工具教出来的习惯是左键负责选择、`Space` 负责移动视图（Figma、Miro 都是），而平移键本来就是大家会去按的那个。这个设置出现之前的手感（直接拖动平移、`Shift` 框选）只隔一个开关，而且两种情况里 `Space` + 拖动和 `Shift` + 点击都有效，试一试没有代价。 |

## 8. 测试

```bash
npm test          # 555 条，37 个测试文件
npm run check     # 版本 + changelog + 类型 + 测试 + 构建
```

测试文件与被测源码同目录，命名 `*.test.ts`。

### 三类测试

**1. 模型层（占大多数）** —— 直接跑纯函数。重点守着 round-trip 不变量：

- frontmatter、CRLF、波浪号围栏、嵌套围栏、有序列表、空列表项、闭合 `#` 的标题
  都能逐字节往返；
- **围栏代码永不产生节点**；
- **任何操作都不碰 frontmatter**；
- 每一次合法的改父级操作，在富文本 fixture 上都还能保持代码内容完好。

**2. 布局层** —— 断言深且不均匀的树里卡片永不重叠（均衡和单侧两种模式），
并且同一棵树布局两次结果完全一致。

**3. 交互层（`interactions.test.ts`）** —— 用一个最小 DOM 桩真正驱动
`attachInteractions` 跑一遍。

### 关于 DOM 桩

`interactions.test.ts` 里有 `FakeEl` / `FakeStyle` / `installDom()`，以及用
`Proxy` 造的 `MapController`（记录调用、返回合理默认值）。

**写桩时最容易浪费时间的地方**是桩本身的缺口伪装成代码 bug。踩过的坑：

- `closest()` 恒返回 null —— 真实元素**自己是自己的 `closest` 匹配**；
- `getBoundingClientRect()` 缺 `right` / `bottom` —— 真实 DOMRect 有这两个边界；
- `style` 有两种写法（属性赋值 `style.left = …` 和 `setProperty`），只实现一种会
  漏掉另一种；
- 缺 `globalThis.HTMLElement` —— `instanceof` 会直接抛错。

结论：**写桩前先把真实 API 的每个细节列清楚**，否则会花大量时间追自己的影子。

## 9. 构建与发布

```bash
npm run dev       # 监听模式，产物直接落到插件目录
npm run build     # tsc --noEmit + esbuild production
npm run check     # 上面那条的完整版本
```

产物是 `main.js`（esbuild 打包，带 banner）、`manifest.json`、`styles.css`。

### 插件审核自己的那套规则

```bash
npm run lint:obsidian            # 审核用的规则集，跑在 `src/` 上
npm run lint:obsidian:locales    # 连英文 locale 检查一起跑
```

跑的是 `eslint-plugin-obsidianmd` 的规则 —— 也就是社区插件审核对一份提交所
应用的规则集，和「能不能编译」完全是两回事。`no-static-styles-assignment` 和
`no-console` 在那边是 **Error**，在这里却是完全合法的 TypeScript，所以没跑过
它就不该发版。

它**刻意不是**插件的依赖：它的职责是检查一份提交，不是参与构建，而且它会拖进
第二个 ESLint 和一堆别的 linter。它有自己独立的 manifest 和 `node_modules`，
放在 `tools/obsidian-lint/` 下，装一次即可：

```bash
npm --prefix tools/obsidian-lint install
```

**要走 npm 脚本，不要直接跑 `eslint`**：ESLint 的工作目录必须是插件根目录，
因为规则是按进程相对路径去读 `manifest.json` 的。没装 `tools/obsidian-lint`
时脚本会以 `2` 退出并打印上面那行安装命令，而不是给一个看不懂的报错。

**Error 会挡住上架，Warning 不会。** 今天它还报着 2 条 warning，都是有意留着
的 —— 两条都属于「规则分不清这个读法是斟酌过的还是随手写的」：

- `i18n.ts` 在 `try` 里读 `globalThis.localStorage`，因为这个属性可能不存在
  （Node、测试环境）也可能抛错（加固过的渲染进程）。而 `localStorage` 是按
  源隔离的，规则担心的那个 popout 窗口看到的是同一份；
- `settings.ts` 仍在调 `display()`，它从 1.13.0 起被 `getSettingDefinitions`
  取代 —— 但本插件的 `minAppVersion` 是 1.5.7，那个版本里两者只有 `display()`
  存在。

### 版本一致性

三个地方必须一致，`scripts/check-version.mjs` 守着它们：

- `package.json` 的 `version`
- `manifest.json` 的 `version`
- `versions.json` 里有对应的 `"<version>": "<minAppVersion>"` 条目

发布时 GitHub Actions 还会检查 **tag 必须和 `manifest.json` 的版本完全相等** ——
Obsidian 就是按这个 tag 去 release 里取文件的，多一个 `v` 前缀是最常见的
「发布成功但装不上」原因。

### 发布流程

1. `npm version minor`（会自动同步三个文件）；
2. `CHANGELOG.md` 加上 `## [x.y.z] - YYYY-MM-DD` 一节
   （`check-changelog.mjs` 会检查，release notes 直接取这一段）；
3. `git push && git push origin <version>`；
4. tag 推上去后 `release.yml` 会跑测试、构建、打包 zip、附上构建来源证明，
   然后创建一个 draft release。

**Changelog 条目是双语的**，中文在前、`<br>` 分隔、英文在后，都在同一行源码里 ——
`<br>` 是刻意的：普通换行在 release notes 里是换行，在 GitHub 上看这个文件时
却会塌成一个空格。

## 10. 代码风格约定

- **注释解释「为什么」，不解释「是什么」。** 变量名已经说了是什么。值得写下来的是
  那个不明显的约束、那个踩过的坑、那个被否决的方案。
- **不写「XX 的测试」这种注释。** 测试名本身就是描述。
- **宁可让类型系统拦住你。** i18n 的派生 key 类型、`assertHandled` 的
  `never` 参数，都是把「忘了一处」变成编译错误的手段。
- **纯逻辑改动必须配套写测试**，放在被测文件同目录。
- **大改动直接重写整个文件**，不要依赖多次小编辑累积。

## 11. 分支约定

`main` 是基线；功能开发走 `feat/*` 分支。发布时从 `main` 上打一个与
`manifest.json` 版本号完全相等的 tag 即可。
